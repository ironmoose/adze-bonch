# Codex runtime adapter

The canonical workflows and role cards remain in the adze-bonch source tree:

- `commands/` contains the single maintained source for each workflow.
- `agents/` contains the five adze-bonch role cards.
- `reference/` and `seeds/` contain the material workflows load when needed.
- The companion prove-it checkout supplies its reviewer and repro-verifier role cards.

Resolve the adze-bonch source root from the checkout containing this runtime file.
Resolve the prove-it source root from the user's explicit adapter configuration or
from the role source path supplied by the installed role inventory. Do not assume a
particular user's home directory or copy canonical prompt bodies into this adapter.
The source checkout must remain readable while workflows run. If a required source
file is missing or inaccessible, stop at that stage and identify the missing path.

The wrappers in `codex/skills/` name the canonical command relative to this checkout;
read that command and follow its current workflow. Read linked seeds, references, and
role cards only as their workflow stage needs them. The wrappers and this file are
routing guidance, not alternate maintained prompt bodies.

## Runtime translations

- Treat `mcp__adze__*` examples in canonical files as calls to the matching adze MCP
  tools. Discover available deferred tools from `ALL_TOOLS` and invoke them through
  the current tool bridge.
- Translate `/adze-bonch:main`, `:status`, `:save`, `:setup`, and `:tackle` to the
  matching `$adze-bonch-*` skill. When a workflow routes to another workflow, read
  that canonical command and continue in the same conversation.
- Resolve `${CLAUDE_PLUGIN_ROOT}` to the adze-bonch source root described above.
  Adapt Claude-only paths and hooks to the current Codex environment; never change
  Claude configuration as a side effect of a Codex workflow.
- Replace Claude `Task` and `subagent_type` dispatch with the available Codex
  collaboration interface. Before dispatch, read the exact canonical role card and
  include its instructions plus the stage inputs in a self-contained task. Use
  `gpt-6-luna` with `fork_turns: "none"` for every delegated role. Preserve the
  role's effort from the source card where supported, defaulting to medium when the
  card has no effort value. Child
  final reports return normally to the orchestrator; do not recreate Claude's
  `SendMessage` pattern.
- Source-card `maxTurns` is an advisory work budget, not an enforced Codex limit.
  For one-turn roles such as the scrum-master and pulse-writer, gather their inputs
  in the parent first and include everything in the dispatch. Do not rely on them to
  make operational tool calls or return for a second pass. For longer source budgets
  (10 to 200), give each dispatch one bounded canonical stage. At its handoff
  boundary, require a report of completed work, remaining work, and verification
  evidence. Verify its outcome before moving forward. Do not compress away required
  work to fit a budget.
- Native agent TOMLs generated by `adapter.py` are valid Codex CLI configurations for
  named role selection where that selector is available. A fresh CLI canary
  dispatched `adze_bonch_scrum_master` with Luna, medium effort, and `fork_turns:
  "none"`; it returned a final report, but the JSON result did not independently
  expose the child model metadata. Treat named dispatch as verified only to that
  extent. The current desktop collaboration bridge has no named-agent selector. In
  that bridge, use the exact source card with explicit Luna, source effort, and
  `fork_turns: "none"`, and do not claim that a TOML role was selected.
- A missing role card is a hard stop for that stage. Do not silently substitute a
  generic agent or omit a required reviewer. Respect platform slot limits by running
  the complete reviewer panel in waves; all required reviewers must return before
  findings are consolidated. On the standard workflow, the panel contains the ten
  canonical prove-it reviewers. Follow the canonical workflow for its workflow-type
  specific panel.
- Additional role roots are opt-in through explicit `PREFIX=PATH` configuration.
  Load only the requested extra card and keep its namespace. If applicable local
  `AGENTS.md` instructions explicitly supply a personal implementer card, prefer it
  as an overlay to the canonical implementer card. The canonical Plan Surface,
  implementation-only authority, TDD order, and stage ownership remain binding.
- The orchestrator owns the workflow and user decisions. In tackle, it remains
  read-only for implementation and tests: the implementer owns code changes and the
  test-writer owns test changes. Keep the canonical TDD order, Plan Surface, review
  scopes, and fix-cycle limits. The test-writer writes failing tests first when TDD
  is enabled; otherwise follow the canonical implement-first route.
- Keep Step 4c.5 repro verification, Step 4d.5 confirmation of each confirmed repro,
  and Step 4e regression-test promotion or an explicit decline with a reason. These
  stages are mandatory as specified by the canonical workflow. A green suite alone
  does not confirm a fix.
- Replace `AskUserQuestion` with a concise question in the conversation and preserve
  the canonical one-decision-per-turn planning behavior. Return workflow results in
  the normal final response.
- When resuming a workflow whose plan the user already approved, continue from that
  plan without repeating its interview. Ask only about a newly exposed decision or
  an unresolved choice that still needs the user's input.
- Read applicable target-repository `AGENTS.md` files before work and `CLAUDE.md`
  files when present. Codex instructions win on direct conflicts. Keep canonical
  lookup chains, synchronous persistence, supersede behavior, and project-context
  updates intact.

## Boundaries and limits

The adapter converts role cards to TOML and emits name, description, developer
instructions, model, and reasoning effort. Source `maxTurns`, tool lists, and sandbox
declarations are carried as advisory text; Codex does not enforce them through these
files. Never describe them as enforced limits. The generated model is `gpt-6-luna`;
preserve the parent conversation's selected model.

`prove-it-gate` remains the quality-gate interface when installed and available on
`PATH`, including its open, verify, confirm-fix, status, and close operations. Codex
file edits are not intercepted by Claude's `PreToolUse` hook, so do not describe the
gate as mechanically blocking Codex edits. The quality-gate and repro-verifier
workflow stages remain required even when the CLI is unavailable.

Keep durable repros in the canonical prove-it repro location, so Claude and Codex
can resume the same verification trail. In setup, probe adze MCP and read the
bootstrap-state before any bootstrap or seed write. Preserve the full host-keyed
`installs:` map, machine-specific fields, discipline drift, and cross-host notes.
Never flatten it to an upstream single-host schema. When setup configures native
specialized roles, run the role adapter's `install` with the explicit prove-it
companion root, then run `check` against that same source inventory. These commands
configure local role files and do not replace the bootstrap probe or authorize
bootstrap writes.
